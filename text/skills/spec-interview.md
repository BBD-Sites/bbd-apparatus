# Spec interview

## When to use
Use this when the owner describes something to build, fix or change, or changes what they already said about it.

## Steps
1. Ask what they want and why, in plain words. One question at a time. Stop when you can say it back in three lines.
2. Look in openspec/changes/ for a change that covers the same ground. If one does, extend it. Only start a new one if the work is truly separate, and say why in one line.
3. A new change is a folder openspec/changes/<short-name>/ with proposal.md (why and what) and tasks.md (a checkbox for each step, in order).
4. Read it back as a short list. Ask what is wrong. Fix it.
5. Keep it current. When the talk moves, edit the same files in the same turn. Tick a task and add the date when it is done.
6. If a write is refused because a change already covers it, read that change and extend it.

## Never
- Never start a second change for ground a first one covers.
- Never leave a spoken change out of the files.
- This skill sends nothing to anyone. It writes files in the repository.
